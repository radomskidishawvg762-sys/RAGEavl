# RAGEval Studio — RAG 质量评估与诊断平台

> **一句话定位**：不只告诉用户「分数是多少」，还告诉用户「为什么失败」「基于什么证据」「修改后是否真的变好」的 RAG 质量工程平台。
>
> 技术关键词：`FastAPI` `SQLAlchemy 2.0` `PostgreSQL` `RAGAS` `React + TypeScript` `LLMOps`

---

## 🎯 为什么做这个项目

它源于一个真实踩坑序列：在开发另一个 RAG 问答系统（学径 AI）并为其搭建双层评估时，先后发现 **5 类「失败被伪装成正常结果」的评估缺陷**——

1. 拒答统计恒为 0（分支判定条件几乎永不触发）
2. `answer_relevancy` 整列 NaN（`np.float32` 非 `float` 子类被静默丢弃）
3. 生成失败被 `except` 吞成占位符，报告却显示 `errors=0`（实测 23.3% 答案失效）
4. RAGAS 覆盖率静默缩水（部分失败与全成功在报告里长得一样）
5. 指标可被措辞刷分（自证式陷阱）

这些盲区说明：**评估基础设施本身就是产品**。RAGEval Studio 把这套踩坑经验产品化，做成了平台。

---

## 🏗️ 核心能力：八段诊断闭环

```text
评估 → 失败检测 → 诊断 → 证据 → 根因 → 建议 → 版本对比 → 回归
```

大多数评估工具止步于第一步（给分数）。本平台的差异点在后七步：

| 环节 | 实现 |
|---|---|
| 失败检测 | 失败按 taxonomy 自动分类（检索失败 / 生成失败 / 数据缺陷……），不与「答得差」混为一谈 |
| 证据 | 每条结论挂 evidence 链，可回溯到具体样本与字段 |
| 根因 | rules 引擎 + 失败模式归因，输出结构化根因而非猜测 |
| 建议 | recommendations 模块给出可执行修复动作 |
| 版本对比 | 同一数据集跨 run 对比，定位「哪类题变好/变坏」 |
| 回归 | 评估配置与指标版本可复现，保证「变好」不是环境噪音 |

## 🧱 整体架构

### 后端分层（FastAPI · 12 个子包）

| 层 | 职责 |
|---|---|
| `api/` | 8 个资源 Router（projects / datasets / evaluations / runs / comparisons / configs / metrics / health） |
| `services/` | 业务编排（`<x>_service`），不直接触碰 Session/ORM |
| `domain/` | Pydantic schemas + 不变量定义 |
| `repositories/` | **唯一数据访问边界**（ORM 查询 + 事务） |
| `models/` | SQLAlchemy 2.0 声明式模型（10 张表） |
| `db/` | Engine / SessionLocal / 连接池 / 健康检查 |
| `runner/` | `EvaluationRunner` 协议 + `LocalAsyncRunner` |
| `engines/` | 评估引擎层：`base`（Protocol）/ `factory`（装配分发）/ `pipeline`（run 级合并与加权）/ `integrity` / `ragas` + `ragas_bridge` / `judge`（判分模型）/ `providers/` |
| `metrics/` | 指标注册中心 + 完整性（integrity）指标族 |
| `diagnosis/` | **技术含量最高的模块**：engine · taxonomy · rules · evidence · recommendations |
| `core/` | config / logging / errors |
| `adapters/` | 外部适配 |

### 前端（React 18 + TypeScript + Ant Design 5 + ECharts）

`pages/ · components/ · api/ · hooks/`，路由：`/` `/datasets/:datasetId` `/evaluations/new` `/evaluations/:runId` `/compare`；运行期 1.5s 轮询进度，终态拉全量报告。前端不硬编码任何阈值/严重度，全部渲染自活跃 Profile。

### 部署形态

```text
应用容器：本地 Docker Compose（仅 app）
数据库：  Supabase Cloud 托管 PostgreSQL（hosting-only，不自托管）
迁移：    Alembic 全量管理
```

## 🛡️ 工程纪律（架构不腐化的保障）

- **8 条架构不变量（I-1 ~ I-8）由测试套件强制执行**，例如：业务层禁止按引擎名分支（`if engine == "ragas"` 违反 I-8）、仓储层是唯一数据访问边界、前端禁止硬编码阈值
- **46 个测试文件**覆盖分层契约、schema、指标完整性、管线审计
- **PRD v1.0 + 技术规格 Spec v1.0 双文档驱动**：非功能需求按 A/B/C 三级约束分层，先定义验收红线再开发
- **可复现性**：判分模型版本、prompt 版本、指标版本写入每次评估记录（metric_version 等 8 个复现字段非空），不同时间的评估结果可横向对比
- **Supabase hosting-only 约束**：仅作为云数据库使用，零 `supabase-py`/Auth/Storage 依赖，数据库代码只存在于 `db/` 与 `repositories/`
